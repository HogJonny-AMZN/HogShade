### The host map: what the schema does not know

Reading the shell against the schema settled what a generator needs beyond the type files: the host's
identifiers (`materialRoughness`, `useRoughnessMap`), labels, UI orders and groups, one Maya semantic
(`OPACITY`), and the flip vector exposed as three sign dropdowns. Everything else the shell declares
(defaults, ranges, choices, colour spaces) the schema already carries, and S1's files already match the
shell's values, which is why the spec can forbid any value change in S2. The map is per host, keyed by
parameter name, and a value the schema knows is a finding in the map. Decided to retire the shell's
four UI macros for explicit declarations: the generator's output is then the thing the S1 union test
parses, with no macro layer to keep in step.
-> the spec, "The host map" and "The generated Maya block"

generated block, 73 declarations, and found four group moves: the retired `HOGSHADE_SLIDER` macro

that were weaker than they read (a dead anchor, a stale allowance). Belief: an equivalence claim about a
file needs an instrument that reads the same fields the consumer reads; fxc and the headless load read
