# ADR-008: what goes under LFS, what never enters the tree, and the hygiene rule

**Status:** Accepted (owner, 2026-09-20 to 26)
**Date:** 2026-09-26, written down 2026-09-27
**Deciders:** the owner

## Context

The legacy repository carried 200 MB of test files and images in history. HogShade rewrote that
history, left the fork network so LFS uploads work, and once pushed an 8K HDR master under LFS by
accident (the orphaned object remains in GitHub's store). The repository is private pending
open-source clearance, and `hog_color` in a sibling repository derives from code written for an
employer.

## Decision

- Git LFS holds only what cannot be generated: the shader ball, the 4K conditioned HDR sources, the
  cooked DDS payloads. 8K masters never enter the tree (`.gitignore content/**/source_8k.exr`).
  Everything that can be generated (manifests, previews, SH9, procedural test data) is generated by
  a tool in this repo and committed as text or small binaries.
- Hygiene before every push: no employer names, personal email only, no files copied from a studio
  tree, Apache-compatible dependencies only. `git grep -n -i -E "bluepoint|sony|bp_py|bp_color"
  -- ':!legacy'` finds no new match. Commits and PRs carry the owner's identity: DCO `-s`, no AI
  attribution.
- The owner's own projects (LargeWorlds, Job_Orchestrator, BATS, SpriteJammer, CO3DEX) may be named.

## Consequences

- A fresh clone is small; a downstream consumer without LFS still builds and tests (CI checks out
  with `lfs: false`; the tests that need payloads skip).
- The generated orchestrator profile carries a `bp_python` path from the dev checkout's canon
  config; it is the owner's call under the clearance gate (board, G1).
- Publishing anything waits on track A of the roadmap.

## Revisit if

Clearance lands (the grep list changes or empties), or a generated asset grows past what text and
small binaries should carry.
