# ADR-007: Job_Orchestrator is the developer track and never a dependency

**Status:** Accepted (owner, 2026-09-26)
**Date:** 2026-09-26, written down 2026-09-27
**Deciders:** the owner

## Context

Verifying a Maya effect needs a GUI Maya on DirectX 11. A scripted `maya.exe -script` launch per
attempt costs a minute of start-up, crashes on some launches, and left idle sessions; two GUI
Mayas crash each other; a retry loop killed the owner's own worker. The owner's Job_Orchestrator
(released as BATS) runs resident DCC workers behind a queue with an MCP server.

## Decision

HogShade keeps its own orchestrator profile, environment files, launcher, submit tool and jobs
(`tools/bats/`, `hogshade/jobs/`), generated by `make_profile.py` and committed, with named worker
types (`hogshade_maya`, `hogshade_maya_gui`, `hogshade_python`, `hogshade_blender`). The developer
track requires the dev checkout at `JOB_ORCHESTRATOR_ROOT`; downstream users never do: everything a
job runs also runs by hand from a committed script, and the repo's tests never depend on the
orchestrator. An agent session reaches it through `.mcp.json`. Rules: never stop a process you did
not start; never launch a DCC beside a running worker; the kill script is human-only.

## Consequences

- The Maya gate that failed for a day by hand passed on the first job; the next check was the same
  job with one parameter (`Docs/knowledge/job-orchestrator.md`, "Where it made the difference").
- Discovery happens once, in the generated profile; a new session reads one page and submits.
- The record of where the orchestrator made the difference is kept on purpose (the journal's
  `→ BATS:` line), because the case for it is built from instances.
- The orchestrator's own gaps (profile by path, sidecar env mappings, a PID kill, job providers) are
  to-dos on the dev checkout, not workarounds here.

## Revisit if

The orchestrator stops being the owner's tool, or a job becomes the only way to run something, which
this ADR forbids.
